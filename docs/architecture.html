Where Ignis sits

Ignis is the Pyr Neural Network layer. Prometheon SI and Lampas sit on top of it; the models sit below it. Ignis is the layer in between that routes the work, holds the shared memory, and carries context across the boundaries.

The stack

Platforms

Prometheon SI (the aggregate model and unified app) and Lampas (the recursive engine) take in work from users and agents. Neither talks to models directly — both go through the network layer.

Ignis — Pyr Neural Network

K5 intent routing decides which model type, vendor, and model should answer; K1 One Memory holds the shared memory every surface reads and writes; K3 carries context with the task as it moves.

Models

The catalog of Approved models — local and API-served — that actually generate the answers. Lifecycle state (Candidate → Approved → Disabled) is enforced at this boundary, at routing and at the Fence.

Routing: the K5 path

On the Prometheon platform the flow is: Input Prompt → Process Manager (classify and decompose) → Decision Intelligence and Reasoning → Decision Options — Model Type, then Vendor, then Model — → Output Generator → Model Output. In Auto mode the K5 router decides the options using a difficulty rubric; in manual mode a user's pick is validated against the roster, Approved records only. Output passes K6 verification with escalation before it is returned, and every turn is a Fence-registered, traced run.

Ignis-platform chats take the shorter path: the gateway hands the turn to the Ignis HTTP service, which answers through the same routing and memory layer.

Memory: One Memory as built

In the pilot, One Memory is one SQLite memory store shared by three surfaces at once: the command-line tools, the generational demo, and the Ignis HTTP service. A fact written through one surface is readable through the others, across models — demonstrated live in cross-model runs. Failed-output write-back is quarantined, so a run whose output failed verification does not write that output into the shared memory; that fix was made and re-verified clean in the pilot after the failure mode was caught.

Grounded in the pilot

Everything on this page describes the pilot build as it stands: Ignis running as a live HTTP service on the pilot host, the gateway routing Ignis chats to it, the shared SQLite memory across CLI, demo, and service, and lifecycle enforced at routing. The console's Routing & Memory panel reads the gateway's live /health and /catalog so the numbers shown are the current routing surface, not figures copied into this page.
